# 容器物理试验

此工程是在上传的星星瓶验证工程基础上拆出的配置化版本，默认提供星星瓶与星星、开盖盒与胶囊、红桶与纸团三组固定配方，不修改原业务仓库。

## 目录


## 打开与运行

打开根目录的 `BetweenUsPhysicsDemo.xcodeproj`，选择同名方案和一个手机模拟器运行，最低系统版本为 17.0，无第三方依赖；真机运行需要在签名设置中选择自己的开发团队。

`Baseline/StarJarSpriteKit` 是上传原件的对照副本，不要误打开它作为新版入口。

## 物理没有因为遮挡被简化

红桶和盒子均使用开放内壁链，包含两侧、转角和完整底部，不会只在口沿放一个碰撞线，也没有实体进入后消失、自动平铺、替换静态占位或停止计算的逻辑。

实体始终保留在场景节点树中，始终有动态刚体以及与内壁、其他实体的碰撞关系，低速后允许引擎正常休眠，新的接触会按引擎规则唤醒；这与“被遮住就冻结”不同。

正常模式的前壁是原图按标定遮罩裁切出的前景，后壁及已经打开的盒盖是后景，实体在两者之间投放，落入后自然被前壁遮住，未修改或重新绘制上传的容器图片。

“透视内部”只改变美术层的透明度，不替换节点、不修改物理体、不改变位置和速度，关闭后从同一物理现场继续显示；“碰撞轮廓”是独立的诊断绘制层，能显示前壁后的完整侧壁、底部以及每个实体的实际几何。

粉色线代表实际开放内壁，绿色线代表实体的碰撞分片，青色线是开口标定参考而不是额外的碰撞盖，橙色点为投放中心。

以后将同构图、同内腔的容器更换为透明美术，只需修改渲染层资源与透明度设置，原有内部物理仍可使用；构图、有效图框或内腔尺寸变化时仍需重新标定几何并递增几何版本。

## 星星基线

新工程的星星两张图片从上传压缩包的资源目录原样复制，文件哈希及与资源副本的比对结果记录在 `Validation/star-asset-integrity.json`，没有覆盖成更早的素材。

原来的 31 点内壁、六块凸多边形、前瓶沿曲线、500 × 724 场景、108 × 108 实体、投放点和抖动范围均被保留，质量、摩擦、回弹、重力、阻尼、速度上限和弹簧拖拽参数也保留；源文件位于基线目录，方便继续比对。

星星图片只是皮肤，新增同剪影的系列与情绪时在配方的皮肤数组登记图片及有效图框，不复制星形几何；目前包中只有这次实际提供的那张星星皮肤，没有伪造其他系列资源。

## 配置与执行器

`Sources/PhysicsCore/ResourceCatalog.swift` 是唯一的产品配置入口，`PhysicsConfiguration.swift` 声明强类型数据结构，`Validation/recipes.json` 是从这些真实配置导出的只读检查数据，不是另一份需要维护的运行时配置。

容器配置持有设计画布、裁窗映射、内壁、开口、墙面材质与前后景，实体配置持有独立几何与质量、摩擦、回弹、线性阻尼和角阻尼，皮肤配置将各自图片的有效图框映射到实体的共同设计框，场景配方把允许的组合、重力、容量、投放和拖拽策略连接起来。

`Sources/PhysicsUI/VesselPhysicsScene.swift` 是三组物件共用的场景执行器，不通过容器名字或实体名字切换算法；几何工厂仅处理凸多边形、圆形和胶囊等原语，素材加载与遮挡则交给独立渲染器。

纸团按手工有效图框裁去外围留白，使用一个近圆刚体，仍允许平面旋转，不模拟软体变形；胶囊按 256 × 256 图片中约 75 × 228 有效图框映射，使用中央矩形与两个圆头凸片组成一个刚体，而不是沿用星星的碰撞体。

胶囊圆头以六段折线近似半圆，每个分片不超过八个顶点，三片仅共享边界而不重叠，避免把完整的圆叠在矩形上改变质量分布；新两组物件的几何和手感属于待真机验收的初始标定，不应把静态检查当作堆叠已经验证。

## 操作与状态

“放入一颗”和“填满容量”都经过同一队列，等待中与场景中的物件共同占用容量，当前每组上限为十个，堵住出生区域时会等待而不强行穿透现有物体。

正常模式不能隔着不透明桶壁点中隐藏实体，透视检查模式可以直接拖动内部实体来检查堆叠和内壁，拖拽只移动无碰撞的弹簧锚点，松手保留引擎产生的速度。

三个场景会分别缓存，切换容器不会重建已装载的物件，暂时没有显示的整个场景不推进模拟；当前场景内被前壁遮住的实体仍完整模拟，这是两个不同的生命周期问题。

“保存现场”将当前配方的内容标识、皮肤、位置、角度、速度、休眠状态及等待队列存入本机，“恢复现场”先校验配方、几何版本、容量、标识和数值有效性，成功后才替换场景，不会把某组容器的位置套进另一组。

快照不是整个物理引擎的序列化，不保存内部接触缓存，也不保证恢复后的轨迹逐位一致，恢复时接触关系会重建；本示例不执行业务同步和内容删除。

越界回收只在实体离开扩展后的场景区域或位置无效时触发，保留内容标识并返回队列，同时增加异常计数，不在正常堆叠中将实体强制吸到底部或推回墙内。

## 接入业务工程

只将 `Sources/PhysicsCore`、`Sources/PhysicsUI` 和实际使用的图片资源加入现有应用目标，不复制演示应用入口、演示界面、基线工程或测试入口，已有同名星星图片应继续保留本地版本。

在稳定持有的模型中创建所需配方的场景，以 `PhysicsSceneView` 嵌入界面，不在界面重算时创建场景，真实内容逐条通过标识入队，避免每次只按数量重建所有节点。

```swift
let scene = VesselPhysicsScene(recipe: ResourceCatalog.paperBin, initialCount: 0)
let contentID = UUID() // 接入时使用业务内容已有的真实标识。
let accepted = scene.queueToken(id: contentID)
scene.onTokenTapped = { id in
    // 业务控制器在这里决定是否进入取出或阅读状态。
}
```

业务仪式准备接管某个物件时调用 `detachForPresentation(id:)`，返回的节点已退出物理世界，位置仍属于原场景，调用方必须显式换算坐标并规划经过开口的取出路径，不能从堆叠中直接沿直线穿墙。

本次盒盖使用提供的已经打开的姿态，没有伪造关闭素材或追加开合仪式，未来开盖、取出、揭示由独立状态控制器执行，不进入碰撞循环。

## 检查与验收边界

生成环境已编译纯核心模块并运行 25 项核心测试，覆盖配置合法性、坐标变换、内壁开放性和完整深度、自交检查、凸片、星星参数回归、队列去重与容量、回收、快照及透明美术和物理数据分离，检查结论见 `Validation/delivery-report.json`，运行记录在 `Validation/core-tests.log`。

所有新应用和场景源码已经过语法解析，工程描述文件通过格式检查，图片保留性另有哈希核对，但这些检查不等于使用苹果系统开发包编译成功，也不证明物理堆叠或渲染效果已经在设备上运行。

当前环境没有执行模拟器编译或设备物理测试，工程另外附带五项苹果框架装配测试，用于在本地确认实际资源、刚体装载、隐藏实体保留、透视切换不替换物理体和快照恢复，这五项在交付前未执行。

在装有开发工具的电脑上可运行下列脚本，指定已经安装的模拟器标识还会运行苹果框架测试，脚本不会安装第三方工具。

```bash
./Tools/validate-on-mac.sh
SIMULATOR_ID=你的模拟器标识 ./Tools/validate-on-mac.sh
```

动态手感仍需本地检查：每组连续投到十个并静置，透视查看隐藏底部有无穿透、长期抖动或异常回收，快速拖拽和释放时检查墙角与开口，切换检查模式前后确认现场连续，再检查退出应用和快照恢复后的标识与数量。

`Validation/geometry-calibration.png` 仅是离线几何标定叠加图，不是物理引擎运行截图，也不是未来显示效果的承诺。
